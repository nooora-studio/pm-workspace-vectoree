## 会议结论摘要

1. 每周需求以飞书「需求管理」多维表格为准，Sprint 作为更直观的迭代看板。**S0 / S1 / S2 表示第几个 Sprint，不是优先级**；不得将当周正在做的需求等同于 S0，按 S0 → S1 → S2 顺序推进，其余入 Backlog。
2. 下周从需求池优先捞取 **S2** 需求进入迭代，其余需求暂入 Backlog。
3. Sprint 1（S1）工作重点明确为 **E1（国内版 vectoree.cn）**、**E2（一键部署 Agent 应用服务）**。
4. 基建类需求先对照现有 Epic，无对应项再新增；本次新增 **E14 数据看板**，并增补 **SEO、Tool Hub 生态、GitHub 生态** 三条 Epic。
5. 种子客户拓展不采用 GitHub 爬取邮箱方案；方案 1 / 2 / 4 推进，方案 3 转为后续产品能力。石瑜评估并细化方案，产研提供支持。

## 1. 飞书多维表格管理规范

### 1.1 本周需求处理情况

已对照本周需求处理情况进行回顾。后续每周需求以飞书「需求管理」表格为准，Sprint 视图作为更直观的迭代看板。

### 1.2 Sprint 序号与排期原则

- **S0 / S1 / S2 表示第几个 Sprint**（Sprint 0、Sprint 1、Sprint 2），不是优先级。
- 不得将「当周正在做的需求」等同于 S0。排期按 Sprint 序号顺序推进：先 S0，再 S1，再 S2。
- 未纳入 S0 / S1 / S2 的需求统一放入 **Backlog**。
- **下周安排**：从需求池中优先捞取 **S2** 需求纳入下周迭代；其余需求暂入 Backlog。

### 1.3 表格与规划展示优化

| 事项 | 结论 |
|------|------|
| 需求描述 | 现有多维表中大量描述不准确，需统一打磨，保证字段可执行、可验收 |
| Sprint 周期 | 冲刺管理的时间周期需调整，与实际迭代节奏对齐 |
| Epic 字段 | Epic 需增加「开始时间」「结束时间」字段 |
| 长期规划展示 | 基于 Epic 起止时间，用甘特图展示产品长期规划 |

## 4. 运营拓展与增长相关

### 4.1 种子客户拓展

已同步运营侧「拓展种子客户」需求的处理进度与方案评估。从 GitHub 爬取邮箱并触达的路径判定为冒进，本次不采用。

已逐项评审四套替代方案，结论如下：

| 方案 | 内容 | 结论 |
|------|------|------|
| 方案 1 | 提交 Awesome List，做被动引流 | **可做** |
| 方案 2 | 邀请裂变（Waitlist + 邀请奖励） | **值得做**；魏琼冰先行评估落地路径 |
| 方案 3 | 一对一私信沟通 | 本期不作为运营主路径；后续可沉淀为**面向用户的产品能力**（提供拉新邮箱与打招呼模板） |
| 方案 4 | 开源 Demo | **可做**；与 Template、Awesome List 结合，建设自有 **Awesome Agent List**（收录高星项目） |

**执行分工**：将上述方案同步给石瑜，由其评估并输出细化方案；产研侧提供配套支持。

### 4.2 Landing Page 优化

Landing Page 外链 Logo 已完成优化处理，并已同步。

### 4.3 SEO 与官网体验

由种子用户拓展与 Landing Page 优化，进一步明确 SEO 相关事项，包括但不限于 `a` 标签、图片等基础优化。

同期确认的官网体验方向：

| 事项 | 安排 |
|------|------|
| 首页增加 QA | 纳入 **Sprint 1（S1）**；下周由魏琼冰推进上线 |
| 首页展示 Model 相关信息 | 参照 OpenRouter 的信息呈现方式规划 |
| 首页增加 Gallery | 不进入本周/下周交付，纳入后续规划 |

### 4.4 API Reference

API Reference 已基于最新代码整理并推至生产环境。评审结论：需移除若干 `api/system` 接口，该类接口为内部接口，不对外文档化。
