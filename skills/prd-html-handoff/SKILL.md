# 面向 HTML 交付的需求文档

## 用途

为这样一套工作流产出 PRD：**前端已由产品侧改完并以 HTML 交付，研发负责其余全部** —— 接口、数据库、服务端规则、权限、异步任务、埋点。

验收标准很具体：**拿到 HTML 和本文档的研发，不问产品一个问题就能完成后端与数据库工作。**

## 这份文档要解决的核心问题

AI 生成 HTML 时，前端看起来是完整的，但只存在于服务端的业务规则往往没人写。这些缺口是固定且可复现的：

- 服务端状态机缺失 —— HTML 用一种形态呈现了三种不同的业务情况
- 「谁能看到这个」从未定义，研发只能重新猜权限
- 幂等未声明 —— 重复发放、重复绑定关系
- 空态 / 加载态 / 错误态 / 无权限态在 HTML 里没有，于是文档里也没有
- 埋点缺失，或只埋了点击、没埋结果

**PRD 的职责是把上述每一个缺口都点名写出来。** 完整审计清单见 `references/handoff-checklist.md`。

## 文档边界规则

每份文档开头都要声明这个约定，并严格遵守：

| 层次 | 事实来源 |
|---|---|
| 布局、样式、文案、静态交互、前端状态切换 | 已交付的 HTML |
| 接口、数据落库、服务端判定、权限、限流、异步任务、第三方回调、埋点 | 本 PRD |

两者冲突时，研发停下并询问 —— PRD 必须明确写出这一点，而不是假装自己能裁决。

## 工作流

### 第一步 —— 读 HTML，前端事实以它为准

动笔前先读完已交付的 HTML 文件或分支。提取：

- 每个页面的路由 / 文件路径
- 每个可交互元素及其各状态（悬停、禁用、加载、错误、空）
- 每个动态区域的每一种视觉状态 —— 它们与服务端状态一一对应
- 全部用户可见文案，逐字记录
- 所有 mock：假登录、`setTimeout` 模拟延迟、写死的演示常量、localStorage key、演示面板、调试入口

把 mock 清单写进 §0.3。**mock 面漏写是生产事故最可能的来源** —— 研发把演示数据照抄进真实逻辑，会同时造成数据污染和逻辑错误。

### 第二步 —— 从上下文重建业务规则，而不是从 HTML 读

HTML 展示的是*某个状态长什么样*，从不说明*它何时发生*。业务规则要从用户提供的材料里重建：既有规则文档、会议纪要、方案文档、口头描述。

对每条规则问一句：研发拿到这句话能写出代码吗？如果不能在不追问的前提下翻译成代码，这条就没写完 —— 按下文**可判定粒度**重写。

### 第三步 —— 写文档

结构与各节撰写要求：

**§0 文档信息** —— 变更记录（只记交付定稿后）、交付物清单、**前端交付说明**（如何查看、mock 面、不可信部分）、发布计划、关联文档。

**§1 背景与目标** —— 要解决的问题、本期做与不做的对照表、后续 §7 埋点要衡量的成功度量。

**§2 需求概述** —— 3 到 5 句：这次要做什么、做完用户能干什么、与现在有什么不同。配一张编号功能点表指向 §5 各节。这一节的作用是让评审者在读细节前先建立正确的整体认知。

**§3 需求涉及范围** —— 本模板的定位章节，存在的理由是前端已完成，研发需要一份明确的地图。

- 3.1 页面 / 模块总览：路由 | 模块 | 改动性质 | 前端是否已交付 | 研发需完成什么
- 3.2 需删除的现网逻辑 —— **单独成节**。删错引发回归，漏删造成双入口或旧逻辑抢占
- 3.3 明确不动的部分
- 3.4 影响面：其他页面、服务、数据表、异步任务、第三方

**§4 流程与逻辑** —— 两种互补表达：

- 4.1 ASCII 分支树表达整体判断逻辑（飞书、GitLab、任意 markdown 查看器都能渲染，不依赖任何插件）
- 4.2 Mermaid 状态机，**配状态定义表**（状态 | 含义 | 进入条件 | 停留时长 | 可能的下一状态）
- 4.3 时序确有必要时用 Mermaid 时序图
- 4.4 判断条件表，写到可判定粒度
- 4.5 异常与边界表：场景 | 触发条件 | 系统行为 | 用户可见表现 | **数据是否落库**

**§5 需求说明（分页面详讲）** —— 全文主体。每个页面固定五段：路径定位 → 页面职责 → 模块拆解 → 状态与边界 → 研发交付要点。

每个模块内部：展示规则、数据来源（字段名、类型、示例值）、交互逻辑、边界（加载 / 空 / 错误 / 无权限），以及**逐字的用户可见文案表格**。

位置引用方式：在 HTML 里标 ①②③，文档引用这些标记。**绝不使用相对位置描述**（「左上角那个按钮」）—— HTML 一改就失效。

**§6 数据与接口约定** —— 只写业务语义，不规定 REST 路径与 DDL，那是研发的决策范围。

- 6.1 数据实体与字段语义；**枚举 / 状态字段必须列全所有取值**，因为前端每种视觉状态对应一个枚举值，漏一个研发就无法正确返回
- 6.2 接口清单：用途 | 触发时机 | 调用方 | 关键入参出参 | 幂等要求 | 失败语义
- 6.3 服务端校验与权限 —— **标出哪些校验必须前后端双写**
- 6.4 时序与超时约定
- 6.5 数据留存与生命周期

**§7 数据埋点** —— 服务于 §1.3 的度量目标。

- 7.1 埋点目标，写成要回答的问题
- 7.2 公共参数
- 7.3 页面 / 模块曝光埋点
- 7.4 关键按钮 / 操作埋点 —— **成功与失败分别打点**，携带 `result` / `error_code`
- 7.5 链路追踪：从入口到终点的编号序列，与 §4.1 主流程一一对应，每步给出流失定义
- 7.6 埋点验收检查

**§8 待确认项** —— 项 | 责任人 | 待决策 | 截止

**可选补充模块**（按需取用，用不到的整节删除，不留空壳）：验收标准、非功能要求、灰度与回滚、需求前后对照。

### 第四步 —— 交付前审计

用 `references/handoff-checklist.md` 逐条核对成稿。每一条要么满足，要么修复，要么移进 §8 作为待确认项。**不带隐性缺口交付文档。**

## 可判定粒度

PRD 规定**业务规则与数据语义，不规定实现方式**。但「只写业务规则」不等于允许含糊 —— 一条规则必须可判定，否则研发回头提问，交付链路就断了。

**不可判定（须重写）：**

- 「建一张邀请关系表记录来源」—— 研发仍要问：哪些字段、何时写入、唯一约束是什么
- 「符合条件的用户展示入口」—— 哪些条件
- 「超时则失败」—— 多长算超时

**可判定（可直接写代码）：**

- 「邀请关系在被邀请人注册成功那一刻锁定；7 天窗口从该时刻起算，不从邀请人的注册时间起算」
- 「入口显隐五条件同时满足：处于项目空间、当前组织为账号默认组织、当前项目为该组织默认项目、`selectedOrganization.role === 'owner'`、该项目尚未物理连通成功」
- 「校验最长 10s，超时按 `FAILED` 处理并展示 Retry 按钮，点击后从 `idle` 重新进入 `checking`」

判据：**研发能不提问就写出那条 `if` 语句吗？**

## 写作规则

- 一条规则只在一处定义，其他位置只引用章节号、不复述。重复定义的规则会各自漂移，研发无法判断哪份权威
- 用户可见文案逐字入表，不改写成描述性文字 —— 研发需要的是准确字符串，不是对字符串的描述
- HTML 里每一种视觉状态，在 §4.2 或 §5.5 都要有对应行。**当 demo 把多种业务情况合并成一种视觉呈现时，在 PRD 里拆开分别定义** —— 这是 demo 式交接中最高频、影响最大的缺陷
- 数据分层：共享产出放 `03_Execution/02_PRD/`，个人思考放 `_Personal/` 且不外发
- 命名遵循 `00_Meta/naming_convention.md`：标题走 `产品 - 需求文档 - 名称`，落盘文件名走 ASCII 安全的 `{type_en}_{name_en}.md`
- 文风客观中立，不加括号式自我标注（「（重点）」「（注意）」），不出现内部调试痕迹、用户名、版本迭代备注
- 图只为降低理解成本而画，说得清就不画，不凑数
