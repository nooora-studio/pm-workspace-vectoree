# 粒度对照示例

改写前后对照。每条贯穿同一个判据：**研发能不提问就写出那条 `if` 语句吗？**

---

## 1. 规则语句

**含糊 → 可判定**

| 含糊 | 可判定 |
|---|---|
| 邀请关系在注册时锁定 | 邀请关系在被邀请人**注册成功那一刻**锁定；7 天窗口从该时刻起算，不从邀请人的注册时间起算 |
| 超时就失败 | 校验最长 10s；超过按 `FAILED` 处理，页面展示 Retry 按钮，点击后从 `idle` 重新进入 `checking` |
| 符合条件的用户能看到入口 | 入口显隐五条件同时满足：处于项目空间（非组织空间）、当前组织为账号默认组织、当前项目为该组织默认项目、`selectedOrganization.role === 'owner'`、该项目尚未物理连通成功 |
| 额度会过期 | 邀请人那笔 $5 入账后 TTL 30 天；被邀请人那笔走现网欢迎额度发奖器，**本期不改现网「到期未充值收回」行为** |
| 老用户点了链接提示一下 | 已有账号点专属链接：不绑定关系、不发奖，提示仅限新用户，并引导去自己的「邀请好友」页 |

**识别信号：** 句子里出现指示代词或范畴词（「这种」「符合条件的」「老用户」「额度」），说明还需要补具体字段、取值或阈值。

## 2. 状态定义

**含糊 → 可判定**

```
含糊：有已发放、已逾期等状态

可判定：

| 状态 | 含义 | 进入条件 | 停留 | 下一状态 |
| 已注册未连接 | 7 天窗口进行中 | 被邀请人注册成功且尚未完成首次有效 link | 至 link 成功或满 7 天 | 已发放 / 已逾期 |
| 已发放 | 双方结算完成 | 被邀请人欢迎额度实际入账 | 终态 | — |
| 已发放（邀请人未得） | 对方已得欢迎额度，但邀请人因满 10 次或对方风控未入账而未得 | 见 §4.5 | 终态 | — |
| 已逾期 | 超过 7 天 | 距注册成功满 7 天且仍未完成有效 link | 终态（对方仍可能得自己的 $5） |

关键：已发放必须能区分「邀请人拿到自己的 $5」与「对方拿到但邀请人没拿到」。
这两态在 demo 里常被合并成一种视觉表现，PRD 必须拆开。
```

**识别信号：** 两种业务情况在 demo 里呈现同一种形态、但服务端行为不同 —— 那就是两个状态。

## 3. 边界行

**含糊 → 可判定**

| 含糊 | 可判定 |
|---|---|
| 重复请求要处理 | 同一对邀请关系重复结算时，第二次调用返回首次结算结果，不重复发放；并发到达时以先落库者为唯一发放方，另一方读到已结算记录 |
| 依赖服务失败 | 校验接口依赖的上游模型服务不可用时，按 `FAILED` 返回并记录 `error_code = UPSTREAM_UNAVAILABLE`；页面展示失败态与 Retry；**不写 `link_success` 记录，不触发任何额度发放** |
| 没数据的时候 | 邀请记录列表为空时展示空态：文案「还没有邀请记录」+ 副文案「复制专属链接发给朋友，双方各得 $5 额度」+ 主按钮「复制链接」；不展示表格骨架以外的任何占位数字 |
| 别人没有权限 | 非本组织成员访问他人 `invite_code` 时返回 404 而非 403，不泄露该邀请码是否存在；页面按未登录态处理 |

**识别信号：** 边界行只有在触发、系统行为、用户可见结果、数据是否留痕四问都答齐时才算完成。

## 4. 埋点事件

**含糊 → 可判定**

| 含糊 | 可判定 |
|---|---|
| 埋点覆盖邀请流程 | 见下方事件表 |
| 记录用户点了复制 | `invite_link_copied`，点击复制按钮且写入剪贴板成功后上报，参数 `invite_code_id`；复制失败上报同一事件名带 `result = fail, error_code = CLIPBOARD_DENIED` |
| 记录注册 | `invite_registration_completed`，被邀请人注册成功**且邀请关系落库成功后**上报，参数 `invite_code_id` / `channel`（`invite_link` 或 `direct`）。注册成功但关系落库失败时上报 `result = fail, error_code = RELATION_LOCK_FAILED` |
| 记录发奖 | `invite_bonus_granted`，仅在额度**实际入账后**上报，参数含 `role`（`inviter` / `invitee`）、`amount`；被风控拒绝时改为上报 `invite_bonus_blocked` 并带 `fail_reason` |

**识别信号：** 每个事件都需要触发时机、参数集，以及任何可能失败时的失败对应事件带错误码。「记录点击」不带成功标记，线上无法区分接口异常与用户流失。

## 5. 字段语义

**含糊 → 可判定**

| 含糊 | 可判定 |
|---|---|
| 关系状态有几个值 | 关系状态共 5 值：`bound`（已锁定，进行中）/ `rewarded_both`（双方均已发放）/ `rewarded_invitee_only`（仅被邀请人发放：邀请人满 10 次或对方风控未入账）/ `expired`（超 7 天）/ `rejected`（已有账号点链接，未锁定）。前端「已发放」标签需能区分 `rewarded_both` 与 `rewarded_invitee_only` |
| 需要记来源 | 关系上记来源渠道 `channel`，取值 `invite_link`（通过专属链接）/ `direct`（无邀请码自然注册）；关系仅在 `channel = invite_link` 时创建 |

**识别信号：** 对任何枚举，数一数前端 UI 实际有几个标签。UI 显示 3 个而规格只列 2 个值，说明漏了一个。

---

## 6. 不该由 PRD 规定的部分

PRD 定义业务规则与数据语义。以下留给研发决策：

- REST 路径、HTTP 方法、请求 / 响应 JSON 结构
- DDL、表名与字段名、索引、迁移脚本
- 框架选型、分层结构、ORM 使用方式
- 用哪个库实现某个行为

例外情形：**当某个现网服务本身是某条规则的权威时**，引用它并描述对齐口径 —— 例如「发奖判定的生产权威是现网 `InstallBonusService`，本文与其对齐；本期不改其「到期未充值收回」行为」。这是对业务行为的约束，不是对实现方式的规定。
